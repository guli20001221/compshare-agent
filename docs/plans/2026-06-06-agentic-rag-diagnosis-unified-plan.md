## 1. North star

One ReAct agent loop where, on a symptom/error-phrased tool-ops or diagnosis turn, the agent **first** calls a real read-only `SearchKnowledge` registry tool to retrieve prior/background tool knowledge from the merged platform+external corpus (**agentic RAG**), **then** optionally calls instance-shaped `Diagnose*` tools for instance-specific analysis, **then** synthesizes a cited answer with **actionable substance** (not a bare citation token). Diagnosis is a **PROCESS**; RAG is an **EVIDENCE STEP inside it** — never a competing terminal route, and never a 4th terminal `tool_ops_qa` intent. The planner's only job for these turns is to land them in the **agent lane** with `SearchKnowledge` available; planner-classification simplification is adopted only to the extent it makes that landing more reliable, and only in its safe, reversible, code-only slice.

This plan builds on **Proposal 1 (Agentic-Loop-First)** as the base and grafts: (a) Proposal 2's external-corpus merge as the literal first phase, its mis-routing measurement harness, and its image-list collapse PR; (b) Proposal 3's retrieval-reach metric and the documented invariant that `IntentDiagnosis` is an agent-form class whose execution shape is agentic-RAG-then-diagnosis. It also corrects the base proposal's mistaken claim that `CompilePlannerCore` is a thin wrap of `compileMinimalPlanCore`.

**The load-bearing prerequisite that the rest of the plan stands on** (and that the original draft mislabeled as "deferred non-blocking work"): the evidence `SearchKnowledge` returns must carry **real retrieved substance**, because on a symptom tool-ops turn the agent has NO instance data to fall back on — the retrieved evidence *is* the entire evidence base. Today's `BuildEvidenceLedger` (`evidence_adapter.go:61-63`) emits a **hardcoded constant summary** — `summary := "Matched platform knowledge entry: " + title` — with NO chunk content, no snippet, no semantic payload beyond the Title. Feeding that to a synthesizing flash LLM for a symptom turn would let it emit a citation token with nothing to ground a real fix. Resolving this is **P3's gated prerequisite** (§4 P3), not deferred.

## 2. How the three threads unify

```
                     ┌─────────────────────────────────────────────┐
                     │  AGENT LANE (RuntimeFormAgent, ReAct loop)   │
  PLANNER            │                                              │
  (Thread 1)         │   step 1: SearchKnowledge  ◄── agentic RAG   │
  classifies a turn  │            (real registry tool, P3,          │
  into ONE class ───►│             returns SUBSTANTIVE evidence)    │
  Level-A:           │                 │                            │
   knowledge ─────────────► terminal_rag (knowledge_qa, unchanged)  │
   diagnosis ────────────►  step 2: Diagnose* tools (instance work) │
   operation/deploy ─────►  step 3: synthesize cited answer         │
                     │                                              │
                     └──────────────────────┬──────────────────────┘
                                            ▲
   RAG KB EXPANSION (Thread 2):  merged platform(687)+external(29) corpus
   is the DATA SearchKnowledge retrieves — vLLM/SGLang/Ollama/ComfyUI
   OOM/kill/port/CUDA chunks. Default-off until parity gate (P0).
```

- **Thread 1 (planner-classification simplification)** decides *where a turn lands*. Its only load-bearing contribution here is keeping symptom Qs in the **agent lane** (P4b boundary fix) and the cheap image-source-as-parameter collapse (P1). The full 24→9 taxonomy cutover and slim-prompt behavioral change are deferred to a successor plan; only the reversible, code-only core compiler ships (P6, shadow).
- **Thread 2 (RAG external-KB expansion)** supplies *what the agent retrieves*. Phases 0+2 are DONE (`#134`/`#135`); this plan merges them (P0) and makes the corpus the backing data for `SearchKnowledge`. Phase 3's terminal `IntentToolOpsQA` is **dropped** (wrong shape).
- **Thread 3 (agentic-RAG north star)** is *how the agent executes* an agent-lane turn: promote `SearchKnowledge` to a real tool returning substantive evidence (P3), put it in the diagnosis tool subset and relax the instance-demand dead-end (P4a), fix the planner boundary so symptom Qs reach the agent lane (P4b), and unify the evidence validator across routes (P5).

The single hinge all three converge on: **`SearchKnowledge` must become a real read-only registry tool that returns substantive retrieved evidence**. Today it is a hardcoded virtual `StepEvent` at two engine sites only and the ReAct loop cannot select it.

### P3 — Promote `SearchKnowledge` to a real read-only registry tool that returns SUBSTANTIVE evidence (flag-gated, default-off)
**Goal.** The single load-bearing prerequisite all three threads converge on, INCLUDING the resolution of the evidence-substance blocker.

**RECONCILE-FIRST (the second SearchKnowledge — do this before adding a registry entry).** A body-driven `SearchKnowledge` already exists in the orchestrator lane (`internal/orchestrator/skill_executor.go:98/106/148`): param `{query}`, a `工具 SearchKnowledge 返回:\n` tool_result wrapper, a budget cap (`SearchKnowledgeBudgetCapsCalls`), returning the **content-free** `BuildEvidenceLedger`. Do NOT ship two `SearchKnowledge` tools with divergent evidence shapes. Prefer **promoting/sharing one retrieval+projection helper** that both lanes call.

Add `SearchKnowledge` to `internal/tools/registry.go` (params mirror the orchestrator: `query` required, `context_hint` optional → `productArea`), with policy in `policies.go`: `Route=ActionRouteKnowledge`, `Class=ActionClassReadCheap`, `NeedsConfirm=false` — survives the `VisibleRegistry` filter (`registry.go:937` hides only `ActionRouteWorkflow`/`ActionClassMutating`) and is **never** routed through `SafeToolExecutor` (`safe_executor.go:180` hard-blocks `Route!=ActionRouteExternalAPI`). Add a **new** `executeTool` branch (`engine.go:2641`) mirroring the existing `knowledge.IsKnowledgeTool` local-exec precedent (same template as `GetGPUSpecs`, `engine.go:2653-2666`): on `action=="SearchKnowledge"`, call `e.knowledgeRetriever.Retrieve(query, inferKnowledgeProductArea(query||context_hint))`, build the evidence payload (see PREREQUISITE), serialize as the tool_result, emit `StepEvent{Action:"SearchKnowledge"}` for trace parity. The two hardcoded virtual sites (`engine.go:1989`, `:3718`) are **UNCHANGED** — this phase is purely additive. Do NOT add it to any tool subset yet (that is P4a).

**PREREQUISITE (promoted from "deferred non-blocking" to a P3 BLOCKER with its own binary gate) — evidence substance.** On a symptom tool-ops turn the agent has NO instance data; the `SearchKnowledge` result *is* the entire evidence base. The current `BuildEvidenceLedger` summary is a hardcoded constant (`evidence_adapter.go:61-63`) with no content — synthesizing on it would let the LLM emit a citation token with nothing to ground a real fix, and GATE A could not pass honestly. **Decide explicitly between two grounded options and TEST it before P3 ships:**
  - **(a) Richer SearchKnowledge projection.** Give `SearchKnowledge` its OWN projection that includes a real content snippet per hit under the citation hard-gate — NOT the diagnosis-evidence boilerplate ledger (the no-raw-Content rule at `evidence_adapter.go:11-13` was designed for diagnosis where the ledger is *supplementary*, not the primary base). This means a new snippet-bearing projector, bounded length, still validator-checked.
  - **(b) Reuse the terminal-RAG EVIDENCE EXTRACTOR (not its message builder).** Reuse `evidencesFromRetrievalHits` (`engine.go:2128`, which sets `Snippet: item.Chunk.Content`) to get full-content `[]envelope.Evidence`, then **serialize that (bounded) as the tool_result JSON string**. **Do NOT reuse `BuildRAGMessages` (`rag.go:69`)** — it returns `[]openai.ChatCompletionMessage`, a TERMINAL one-shot message array, which a ReAct tool cannot return (the loop needs a serialized string it appends and continues from). ## 7. GO / NO-GO decision gates

This plan has **two** explicit decision gates. Everything else is a binary per-phase ship/no-ship.

**GATE A — Agentic-RAG reachability (resolves at P4b, blocks P5 flip; presupposes the P3 substance gate already passed).**
*Question:* Does the agentic loop actually rescue symptom-phrased tool-ops Qs with a SUBSTANTIVE answer?
*Precondition:* P3's substance gate is GREEN — `SearchKnowledge` returns chunk-grounded evidence (not the content-free ledger), the no-raw-leak/cite guard is INSTALLED on the agent-lane synthesis (P3, not P5), and every probe in the symptom set is corpus-COVERED (the set already substitutes the covered `sglang 显存不足` → `ext-sglang-oom-001` for the corpus-uncovered `sglang 端口连不上`; author `ext-sglang-port-*` before reintroducing a port-specific probe). Without these, GATE A cannot be evaluated honestly: a bare-citation answer would pass a naive "cite ≥1 chunk" check while being useless, and an uncovered probe would NO-GO for a corpus gap mis-read as architecture failure.
*Evidence that resolves it (Proposal 1 P5 gate, hardened with Proposal 3's retrieval-reach metric):* with `COMPSHARE_AGENTIC_SEARCH_KNOWLEDGE=1` and `COMPSHARE_EXTERNAL_KNOWLEDGE=1`, the P2 harness **corpus-covered** symptom set ("vllm 进程被 kill", "sglang 显存不足", "vllm serve 报 ValueError") at N≥5 each shows: a `SearchKnowledge` `tool_call` BEFORE any `Diagnose*` call, **retrieval-fired=true ON the external corpus** (the chunk IDs cited are vLLM/SGLang external chunks — not just "no mis-fire on billing/stock"), the synthesized answer carries **actionable substance from the cited chunk** (concrete flag/command/cause, not a bare citation token), `ActualRuntimeForm=="agent"`, no "which-instance" dead-end, AND genuine platform symptoms still get clarified, AND `ValidateNoRawEvidenceLeak` passes. **GO** ⇒ proceed to P5 default flip. **NO-GO** ⇒ keep the agentic path flag-off, re-examine the P3 evidence shape, the #123 boundary, or the subset/relax wiring; do not flip the default.

**GATE B — Planner core-schema cutover (OUT OF THIS PLAN's committed scope; resolves in the successor plan).**
*Question:* Should `PLANNER_SCHEMA_MODE=core` (slim prompt, behavioral cutover) ship?
*Evidence:* the deferred Phase-7 dual-run (full vs core) with three metric families — `schema_valid_rate` (core not worse than full, 0.98 floor), `intent_match_rate` (not worse on the #123 / how-to / image-routing mismatch classes), AND the **retrieval-reach** metric (external corpus retrieved on vllm/sglang symptom turns). Binary GO/NO-GO, not averaged. **NO-GO still keeps P1–P6 value** (intent roles + net-new core compiler + the agentic loop stand on their own), so abandoning core-emission is cheap. This plan deliberately ships only the `core_shadow` observe-only slice (P6); the cutover is a successor PR behind Gate B.
